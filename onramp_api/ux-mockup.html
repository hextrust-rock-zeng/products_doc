Stage 1 — Discovery

HubPay's app fetches the supported pairs for Alice's onboarded jurisdiction (SVG). The result is jurisdiction-scoped server-side, so Alice only sees pairs she's actually licensed for.

REQUEST
GET /onramp/availablePairs

Stage 2 — Quote

HubPay's backend requests a live quote bound to the pair × chain combination. Hex Trust polls its LP (Ripple), applies the spread, and returns a quote valid for 5 minutes. Alice sees a locked rate before committing.

REQUEST
POST /onramp/getQuote
# Body:
{
  "fiatCurrency":   "USD",
  "cryptoCurrency": "USDC",
  "chainId":        "1",
  "fiatAmount":     "100000.00"
}
RESPONSE — 200 OK
{
  "quoteId":         "73797374-656d-4000-8000-00008badf00d",
  "fiatCurrency":    "USD",
  "cryptoCurrency":  "USDC",
  "chainId":         "1",
  "chainName":       "ethereum",
  "fiatAmount":      "100000.00",
  "cryptoAmount":    "99950.00",
  "ratio":           "0.99950",
  "inverseRatio":    "1.00050",
  "validTimestamp":  1741123756789
}
What's happening: The rate is firm at 0.99950 for 5 minutes. HubPay's UI shows a countdown timer. Alice's wire (still days away) will execute at exactly this rate — Hex Trust absorbs any LP drift during the wait. No webhook yet — quote is informational only.

Stage 3 — Accept quote, receive bank instructions

When Alice taps "Accept quote," HubPay calls acceptQuote with the quoteId. Hex Trust binds the rate, resolves the crypto destination from Alice's pre-whitelisted wallet, and returns multiple bank accounts she can choose from.

REQUEST
POST /onramp/acceptQuote
{
  "quoteId":       "73797374-656d-4000-8000-00008badf00d",
  "clientOrderId": "hubpay-onramp-12345"
}
RESPONSE — 200 OK
{

Stage 4 — Waiting for fiat

During the 1–2 day SWIFT clearing window, HubPay's UI shows a live status tracker. Behind the scenes, HubPay listens for webhooks; for resilience, they can also poll orderStatus.

OPTIONAL POLL
GET /onramp/orderStatus?orderId=73797374-...
RESPONSE — 200 OK
{
  "orderId":                  "73797374-...-00008badf00d",
  "orderStatus":              "ORDER_CREATED",

  "cryptoAmount":             "99950.00",

  "settledAt":                null,

Stage 6 — Settled (terminal — success)

The on-chain settlement transaction confirms (block-confirmation count reached). The final webhook fires. Alice's view flips to the success state — USDC is in her wallet, viewable on Etherscan.

What's happening: Order is now terminal. HubPay updates its books, sends a receipt, and stops listening for further events on this orderId. End-to-end elapsed time: ~25 hours (most of which was Alice's bank's SWIFT clearing). Alice can buy more — the next round is a fresh quote.

End-to-end journey summary

From quote to delivery — what Alice experiences vs what HubPay's backend does.

# Alice's view HubPay → Hex Trust Hex Trust → HubPay (webhook) Elapsed
1 Picks USDC · Ethereum GET /onramp/availablePairs — 0s
2 Enters $100k, sees locked rate POST /onramp/getQuote — +2s
3 Sees bank instructions, sends wire POST /onramp/acceptQuote 🔔 ORDER_CREATED +10s
4 Status: awaiting wire — (optional poll orderStatus) — +24h
5 Wire confirmed, trade executing — 🔔 FIAT_RECEIVED + 🔔 TRADE_EXECUTED +25h
6 99,950 USDC in wallet ✓ — 🔔 TRADE_SETTLED ✓ +25h 5m
Integration footprint for HubPay: 3 API calls (1 GET + 2 POST), 1 webhook endpoint, 7 event types to handle. Schema is near-identical to Convert-to-Pay, so a CTP integration can be extended in days, not weeks.
