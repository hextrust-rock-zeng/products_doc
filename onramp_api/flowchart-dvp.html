2. Architecture decisions

ADR-001 — DvP-atomic (not pre-fund)

Decision: Atomic per-quote orders. acceptQuote returns bank account + reference, client wires fiat, ops manually confirms CL1, crypto settles to client wallet. Hex Trust does NOT hold client fiat balances — fiat is in-flight only.

Why:

  • Stablecoin inventory → rate-lock during multi-day wire carries near-zero FX risk (USDC/USDT track fiat ±0.1%).
  • Decoupled price source vs execution venue → LP (Ripple Phase 1) provides the live price at getQuote time; the trade executes from Hex Trust inventory, not against the LP. The locked rate can be held for the full order window without forcing a short LP-hedge window. Hex Trust absorbs LP-price drift during the window — safe for stablecoins.
  • DvP via ops → manual CL1 confirmation in HexAdmin is the gate satisfying "settle to us before we settle to you."

Consequences: no client balance → no e-money / SVF / safeguarding scope debate (§9). API near-perfect mirror of CTP. Pre-fund model preserved for Phase 2.

ADR-002 — Separate endpoint set (/onramp/*) — unchanged

/onramp/* parallel to /convert-to-pay/*. Future /swap/* for crypto-to-crypto. Symmetry enforced (auth, webhook envelope, error namespace, pagination) so a future unified /trade/* is a docs-only re-skin.

ADR-003 — Phase 1 scope freeze

Decision: this design holds explicitly for stablecoin Phase 1 with inventory-funded execution. Phase 2 (volatile pairs or LP-hedged) reopens ADR-001 — revisit pre-fund or re-quote-at-arrival. Do not retrofit this design blindly.

6. Webhook events — mirror of Convert-to-Pay

Payload shape — CTP-style envelope: { payload: { eventType, id, currentWebhookCallAt, eventTriggerAt, firstWebhookCallAt, retryNum, data: { orderId, clientOrderId, order }, metadata }, signature }. The data.order field is a full order snapshot (identical to GET /orderStatus response), reflecting post-event state. Clients dedupe by payload.id. Signature is base64-encoded Ed25519 over the JSON-marshaled payload field (asymmetric — client verifies with Hex Trust's public key distributed at onboarding).

Same envelope as CTP: at-least-once, Ed25519-signed (in body), flat per-webhook-URL retry interval configured at onboarding, dedupe by payload.id. Webhook delivery to clients is handled by the Webhook Service, triggered by OMS. OMS is the central coordinator: it receives state-change notifications (from Settlement Engine), propagates them to RFQ Engine, and triggers the Webhook Service to fire the corresponding webhook. The API Gateway handles only inbound REST traffic.

7. What's different from Convert-to-Pay

Three differences, all consequences of fiat being slow:

  1. DvP gate on settlement. CTP: on-chain crypto deposit confirms (fast, auto), fiat payout fires. On-ramp: ops manually confirms CL1 in HexAdmin before CL2 fires. Same state machine, different trigger source.
  2. Inventory check at quote time. getQuote verifies enough stablecoin inventory to honour the trade (above a floor reserve). CTP has no inventory dependency.
  3. Refund destination is the originating bank account only. Source-of-funds match. CTP refunds crypto to the sending on-chain address (well-defined); fiat refunds need explicit bank-account matching for compliance.

8. Inventory considerations

Inventory management is NOT a blocker for the on-ramp API. Phase 1 deliberately keeps inventory logic minimal — automation falls back to manual when liquidity is insufficient.

ConcernPhase 1
Price source at quoteLP (Ripple) — live indicative price + Hex Trust spread
Inventory pre-check at quoteNot required for day 1. getQuote does not gate on inventory level
Insufficient inventory at execution timeAutomation fails → Slack notification to traders + ops → manual settlement

9. Regulatory note — significant simplification vs pre-fund

Compared to pre-fund (rejected in ADR-001), DvP-atomic eliminates the client-money question:

  • No client fiat balance held → no e-money / SVF / account-issuance / safeguarding scope debate.
  • Fiat in-flight during the order window fits cleanly under Singapore MPI's Cross-Border Money Transfer Services + DPT Services.
  • The trade itself fits VARA Broker-Dealer Services + MAS MPI DPT OTC Trading.
  • HK trustee structure unaffected.
  • Path A (partner bank holds fiat in safeguarded/FBO account at Zand/BCB) applies trivially.

Compliance sign-off still recommended on order window length and refund flow, but the gating client-money question is no longer in play.
