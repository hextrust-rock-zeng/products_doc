Phase 1 = stablecoins: crypto leg carries near-zero price risk (track fiat ±0.1%), so LP-hedge is trivial and held-balance FX exposure is negligible. Volatile-asset pairs are Phase 2.

2. Architecture decisions

ADR-001 — Pre-fund model (not atomic quote-first)

Decision: Client wires fiat first → ops confirms into a fiat balance → client trades against balance. Quotes are executable only when sufficient balance exists.

Why:

  • Matches Hex Trust's actual current OTC desk behavior (per JY): we wait for client funds, then quote.
  • Matches the institutional industry standard — Coinbase Prime, BitGo, Kraken, Bitstamp all pre-fund-then-trade. Atomic quote-first is the retail pattern (MoonPay, Stripe).
  • Dissolves the rate-lock-over-slow-wire problem — the slow bank rail happens before quoting, so the quote can be a normal short RFQ (~60s).
  • Eliminates 3 edge cases: partial deposit, mid-trade overpayment, late-wire re-quote all vanish.

Trade-off: holding client fiat balances introduces safeguarding/segregation obligations (see §7).

ADR-002 — Separate endpoint set (/onramp/*)

Decision: /onramp/* is new, parallel to /convert-to-pay/*. Future /swap/* serves crypto-to-crypto.

Why: pre-fund on-ramp behaves like a mini-brokerage account (deposit → balance → trade → refund) — structurally different from CTP's atomic deposit-address-per-quote. Mirrors how Coinbase keeps Onramp / Prime / Convert separate. Symmetry enforced (auth, webhook envelope, error namespace, pagination) so a future unified /trade/* is a docs-only re-skin.

4. Two decoupled lifecycles

The fiat-balance side is slow and ops-gated; the trade side is fast and atomic because the balance already exists. They touch only at acceptQuote (balance debit).

REFUND_REJECTED ✗Ops rejected refund (e.g. bank mismatch)refundId, reason

Same envelope as Convert-to-Pay: at-least-once, HMAC-signed, exponential-backoff retry, dedupe by orderId/depositId/refundId + eventType. getQuote → acceptQuote is one fast round-trip, so ORDER_EXECUTED and ORDER_SETTLED may collapse into one event.

8. Compliance flag — client-money safeguarding

The single genuinely new risk vs the pass-through CTP model: holding client fiat balances may trigger client-money safeguarding / segregation obligations, and possibly e-money / deposit-taking considerations, depending on the issuing entity's jurisdiction (SG / UAE / HK). Clear with compliance before build:

  • Are held fiat balances segregated from Hex Trust operating funds?
  • Which entity holds the balance — is the activity within its license scope?
  • Maximum hold period or balance cap per client?
